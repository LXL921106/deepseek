# 评估与回归

这一层只回答一个问题：**改完规则，是退步了还是进步了？**

它**不**回答"戏写得好不好"——那是创作者的判断，靠真实产出去评，不靠这里的分数。

## 回归门禁

```bash
python gate.py
```

对 `cases/` 下每个案例运行 `scripts/` 里的全部校验器，核对咬中的规则 ID 是否与 `expected.json` 一致：

- `must_fire`：必须咬中的
- `must_not_fire`：不得误报的

全绿才算通过。红了说明要么规则漏了，要么规则误伤了。

（DSH 环境用捆绑 Python：`~/.dsh/dsh-runtimes/*/dependencies/python/python.exe`。）

## 案例怎么加

一次真实交付里发现了新缺陷 → 把它缩成最小合成夹具 → 写进 `cases/<序号>-<名字>/`：

```text
cases/NN-名字/
├── script.md        剧本（约定 `名字：台词`）
├── delivery.md      交付物（提示词）
├── ledger.md        台词逐句回勾表
└── expected.json    must_fire / must_not_fire
```

**必须成对加**：埋缺陷的案例 + 正确交付的案例。只加前者会让门禁越来越严，最终到处误报。

## 为什么不用 `examples/` 代替

`examples/` 里的样例是**手工塑形的**，所以只覆盖我们**想到过**的情况。历史缺陷全部从它们旁边走过去，原因是同一个——样例里没有那种输入。

所以 `cases/` 是**为已知缺陷专门造的**，不是随手写的范文。这两者回答不同的问题：

| 目录 | 回答 |
|---|---|
| `examples/` | 产物长什么样 |
| `cases/` + `gate.py` | 按文档从头走一遍，还跑得通吗 |

## 尚未覆盖

`AST-01`、`FMT-01`、`PRJ-01` 还没有校验器；`cases/*/expected.json` 的 `not_yet_implemented` 字段记录着当前缺口。

## 每次改规则后

1. 跑 `python gate.py`，全绿。
2. 如果加了新规则，**先加一个能证伪它的案例**，再加规则。
3. 如果发现案例本身写错了（期望值与分级不符），改案例要说明理由——不要为了让门禁变绿而放宽期望。
