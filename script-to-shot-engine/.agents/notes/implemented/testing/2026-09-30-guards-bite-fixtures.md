# Agent Note: 门禁必须用夹具证明它会咬人

Status: implemented

## Problem

写着规则不等于规则生效。新写的校验器**本身就出过两个 bug**，而且两个都不会被"读一遍代码"发现：

| bug | 表现 |
|---|---|
| 说话人被解析成「沈志远开口说」 | 已经写在正文里的台词被误报"整句缺失"；同时 **`DIA-03` 残句检测完全没触发** |
| `check_timeline.py` 的 JSON 不输出 `fired` | 门禁读不到它咬中了什么，于是"有阻断项"和"没阻断项"看起来一样 |

第一个 bug 尤其危险：它同时产生**假阳性**（误报已写的台词）和**假阴性**（漏掉最该抓的残句）。只看代码是看不出说话人名字里混进了动词的。

## Decision

`evaluations/cases/` 下每个案例是一组合成夹具加一份 `expected.json`，声明：

- `must_fire`：必须咬中的规则 ID
- `must_not_fire`：不得误报的规则 ID

`evaluations/gate.py` 跑全部案例并核对，任一条不符即红。**案例必须成对**：一个埋缺陷的案例证明门禁会咬，一个正确交付的案例（`02-clean`）证明门禁不误报。

## Alternatives considered

- **只写单元测试直接调用函数** —— 最强理由：更快、更细、能定位到具体分支。不采用：脚本真正的用法是命令行加文件，测函数会漏掉参数解析、文件编码、JSON 输出这些真实失效点——`fired` 字段缺失正是这一类，函数级测试抓不到。
- **只保留埋缺陷的案例** —— 最强理由：案例少一半、维护轻。不采用：只测"会咬"会持续鼓励把门禁写得越来越严，最终到处误报；`02-clean` 是防止这一点的唯一约束。

## Consequences

- **收益**：改规则后能回答「是老问题复现还是新问题」，不再靠感觉；门禁自身的 bug 会被夹具暴露——本文件的表格就是它俩被暴露的记录。
- **代价**：案例是**合成的**，仍然覆盖不到没想到的输入。与真实实跑的差距要靠继续把真实交付里的缺陷缩成夹具来补，而不是靠多写案例。
